# agent全自动生图 · 踩坑记录

## 已确认问题
- **★★ 保留清单里写条件项「如果有 X 就保留 X」= 邀请模型幻觉，它找不到就从背景搬一个来**（2026-07-27 S1 首跑实锤，改后复跑通过）：S1 白底SKU重生成卡出图，产品腰头上多出一块花体 `Nmpx` 织唛——来自原片里产品**背后那件针织毛衣**的自带织唛。根因是提示词的保留清单里我写了一条条件项 `The waistband's inner label if it is visible`，模型据此去找标，找到背景毛衣的织唛就认成腰头内标搬了上来。**修法三条**：①删掉条件项，改成点名唯一确定存在的那个 logo ②在「必须删除」段写死"背景上的任何织唛/吊牌/绣标/印字/logo 一律随背景删除，禁止迁移到产品上"，并正面陈述"腰头是光的"③预判模型的误认路径并直接堵死："如果你觉得腰头上方有块标，那是背后针织物的，删掉"。复跑一次即消失。**推广口径：保留清单只能列确定存在的东西；不确定的要么点名禁掉，要么根本别提。** 这与 R12（参考图元素吸附迁移）同类——模型对"产品附近的视觉元素"有强吸附性，离产品越近越容易被吃进去，抠背景类任务尤其要点名背景里贴着产品的那些标记。本条为第一次项目验证，暂不晋升知识库。
- **★★ 记忆库推了 ≠ 代码推了；异地项目当天不 push 项目仓库，第二天就得整段重做**（2026-07-27 实锤）：07-26 家机把 V14 重构了一遍（蓝图+提示词全改），记忆写了、记忆库推了，**但项目仓库没 commit 没 push**。07-27 到公司机 `git fetch` 仍停在 07-25，那版改动拿不到；家机不在手边，只能按记忆里的改动清单在公司机整段重做（约一小时）。**能重做的唯一原因是记忆写得够细**（改哪几张卡、砍什么、新增哪几条护栏都记了），否则就是纯损失。教训两条：①**收工检查第 4 步「项目代码已 push」不是走过场**，异地双机项目当天不推=第二天必堵；②两台机器出现分叉时**不要合并**——落后那台直接 `git reset --hard origin/main`，同一批文件两个手写版本互撞的代价远大于重做。
- **★ 输入槽可空 + 靠位置认图 = 歧义，必须用数据层字段消解**（2026-07-27 设计判据，★首轮实跑待验）：V14.1 的 IN1/IN2/IN3 是产品图、最后一张是色准图，但槽位允许空——一旦 IN3 空着，色准图就变成"第三张"，模型无从判断最后一张到底是产品还是色准，结果要么少画一件要么把色准图当第四件产品画进去。**修法不是在提示词里写更聪明的判别话术，而是在需求卡里加两个字段**（`Pieces = N`、`Colour reference = 有/无`），提示词和 QA 都以字段为准。**推广口径：凡是"输入数量可变 + 按位置认图"的节点，数量和类型必须由数据层显式声明，不能让模型推断。** 这与"场景抽进数据层"是同一条思路的另一次应用。
- **★★ 编辑式里 AI 的构图自由必须按「形变量」分级放开，平移缩放安全、三维形变=重画**（2026-07-26 设计判据，★首轮实跑待验）：给多张平铺白底图让 AI 合成一张多件场景图时，**摆位置（平移、缩放、错位对角、边缘轻微交叠）只是二维变换，产品像素基本原样可用，低风险**；一旦要求「折叠起来堆在后排」「立起来」「卷一卷」「转个侧角」，AI 必须重新推算三维形态，等于重画产品——logo 和版型当场崩。修法：提示词里把这条**显式写成两段**——正面写清允许的排布自由（错位/大小微差/轻微交叠/留呼吸空间），反面把折叠/立起/卷起/立体/侧角逐个点名禁掉，并在 QA 加对应硬失败。**推广口径：编辑式放开任何构图自由前，先问「这个操作需不需要模型推算新的三维形态」——需要就是重画，不需要就能放。**
- **★★ 别人产品的参考图不能喂进生图卡，纹理会串到自己的产品上**（2026-07-26 判定，R12 的反向应用）：商家给的 12 张「新式」参考图，产品是**提花棉**（表面立体小花），我方产品是**纯色无纹理**。R12 已实锤面料参考图会被模型当风格/颜色提示、纹理会吸附迁移——反过来同理，喂提花参考进去，纯色产品很可能被画上提花暗纹。**正确做法：参考图只给人看、由人拆成文字规格写进提示词与需求卡（摆位方式/机位/光型/景深/台面明度/道具清单），图本身不进画布。** 多喂一张参考图 = 多一个污染源。
- **★ 编辑式把「补拍」的成本压到极低，不该按传统重拍估价**（2026-07-26 方法论）：编辑式下 AI 负责换背景、重打光、加道具、造景深，所以原片**只需要构图和产品形态对**，光烂、背景乱、稍微糊都无所谓（那些正是要被换掉的部分）。所以「补一张手持照」= 手举着产品、随便找面墙、手机拍一张，五分钟；不是「重拍」= 棚+灯+桌面+道具。**客户抗拒「重拍」时先做这个区分**，很多时候他抗拒的是传统拍摄的成本预期，不是拿相机这个动作。
- **★★ Joe 验收通过 ≠ 终端商家验收通过，两道闸必须分开记**（2026-07-26 实锤）：周周内裤 8 张详情图 07-25 Joe 判可交付并记为「验收通过」，07-26 商家原话「太老式啦」「其他看着还可以，不过是老式的拍摄手法」「可能就是没有什么亮点，肯定要拍点搞点亮点出来」，整套驳回。**教训：交付类项目的记忆里，「验收通过」必须写清是谁验的；只有终端付钱方点头才算过。** 中间验收过了就写「Joe 验收通过，待商家确认」。
- **★★ 商家嘴里的「老式 vs 新式」是可拆解的构图语法，不是玄学**（2026-07-26 拿到商家参考图 12 张后拆解）：老式 = 米色亚麻台面 + 多条叠放同一平面 + 顶部横幅压粗黑标题 + 正俯视无层次。新式 = ①**深色台面托浅色产品**（深棕木桌+深木圆托盘，靠明度反差把产品顶出来）②前景主体清晰 + 背景堆叠轻微虚化，有景深 ③固定一套 ins 道具（留白书封的外文书/米白针织布/藤编角），逐帧一致只移动取景框 ④**矢量卖点标注**（白虚线箭头+尺寸数字、虚线圆弧勾结构、盾牌图标）⑤杂志式小字排版（左上多行左对齐小字，不压矩形底不居中不粗黑）⑥手持展开。**推广口径：客户说「没亮点」时，先问他要参考图再逐条拆构图语法，别自己猜审美。** 其中「深色台面托浅色产品」这条最反直觉——浅色服装的详情图本能会配浅色台面，结果产品陷进背景。
- **★★ 手持展示是编辑式的硬边界，AI 做不了**（2026-07-26 判定）：商家参考图 12 张里 6 张是手捏腰头提起。编辑式的前提是「产品像素当既成事实保留」，而加手要①凭空生成一只手（生成式最经典翻车区）②重画被捏起的布料形变——前提当场崩塌。**只能真拍。** 好消息是手持不是「新式」的必要条件：深色托底+ins道具+矢量标注+小字排版四条无手也全做得到，参考图里另外 6 张就是无手的。
- **正俯视白底图放进带透视的场景 = 产品变贴纸**（2026-07-26 设计时预判并写进 GS 护栏，★首轮实跑待验）：白底SKU图是相机正对桌面垂直向下拍的，产品是无透视的平面；若场景生成成 45° 俯角（圆托盘成椭圆、桌面有汇聚线），两者透视不一致，产品会像 PS 贴上去的一张纸。修法：**场景机位跟输入图对齐，锁死正俯视**，并在需求卡里注明「机位不在场景卡定」，防止场景池里的角度描述跟提示词打架。配套必须写死接地阴影，否则产品悬浮。**推广口径：合成/换背景类任务，场景机位必须跟产品图机位对齐，这是比光线更先决的一致性。**
- **apply 出来的画布别再手动拖卡/连线，会把它搞乱**（2026-07-24 实锤）：V14 画布 apply 时 11卡/15连全对、verify 通过，但之后我在上面手动怼测试连线，再查已经变成 34卡、QA 入边一条不剩。且平台的 `apply {"connections":[...]}` 不带 cards 会报 400，没法单独补一条边。**结论：画布是蓝图的只读投影，要改就改蓝图重 apply；结构一旦乱了直接 apply 成新项目，不要在坏画布上缝补。** 这跟"结构性改动 apply 新项目不原地升级"是同一条铁律的延伸。
- **AI 复刻真实品牌商标进商用图=侵权，道具类提示词必须写死品牌红线**（2026-07-24，Joe给的ins桌搭参考图里有DIOR/JoMalone/LA MOUSSE真logo）：生活化场景放护肤品/香水/书/键盘当道具时，模型会照着参考图把真实品牌名和logo也画出来，进商用图有商标侵权风险。修法：凡是带道具的场景，提示词写死"道具一律无真实品牌名/logo/商标，瓶身书封留白或无意义装饰字"，并点名常见牌子严禁复刻；**产品自身的logo不受此限**（那是客户自己的品牌）。这条对所有放生活道具的电商生图线通用。
- **暖白渐隐没有矩形边界，也照样会把浅色商品洗曝光**（2026-07-25 周周内裤 PS 保色修正版实锤，修正同日早先结论）：二版用 76%–80% 暖白高斯模糊层承托文字，视觉上没有硬盒子，但它覆盖了商品上方与边缘。逐区域量化显示：顶部平均额外增亮约 +18～+30，商品边缘区域约 +6～+24；浅绿色与浅粉色因此被洗淡。删除全部渐隐层后，商品边缘区域“新增亮度 >12”像素占比 8/8 均不高于 0.001%，最大值为第 05 张的 2 个抗锯齿像素（0.000375%）。**推广口径：低饱和服装详情图不要让任何白色云雾、曝光或调色层跨到商品；系列感由字体、编号、细线与对齐建立。没有实物/色卡真源时，后期应零增亮、零调色，不替用户猜色。** 本条为第一次项目验证，暂不晋升知识库。
- **详情图“统一”不等于八张同一个模板——大面积白底 + 固定左对齐会迅速变成工厂模板感**（2026-07-25 周周内裤 PS 二版实锤）：首版 8 张都用顶部半透明暖白矩形、同一粗标题与同一对齐方式，功能可读但 Joe 判“平平无奇”。后续改为中文衬线标题上下两级、英文字标、细线、超大低透明页码，并在同一颜色/字体系统内轮换左编辑版、右编辑版、竖条编号版三种节奏；最终保色版不再使用任何暖白承托层。**推广口径：系列感由字体、颜色、字号层级建立；差异感由对齐、编号锚点和留白方向建立。八张同位置只换字，不叫统一，叫模板复制。** 本条为第一次项目验证，暂不晋升知识库。
- **★★ 生成式救不了的，换成编辑式就没了——「让AI重画产品」vs「让AI只换背景」是两条路**（2026-07-24 V14 实锤，本项目最重要的方法论转折）：前五条产品线全是**生成**指令（给参考图+文字，让模型重新画出这个产品），于是 logo 写错字、颜色漂、版型被偷改、纹理被吸附——**这些全是"重画"这个动作本身带来的，不是提示词不够好**，在纯色无纹理+中文logo的品类上连调两天全部不过关。改成**编辑**指令后当天通过：**用户自己摆拍好的照片当构图与产品真源，产品像素当既成事实保留，AI 只负责换背景、重打光、抚平表面褶皱**。写法关键三条：①开头写死"You are RETOUCHING a real photograph, you are NOT creating a new photo"②逐项锁死（形状/位置/旋转/缩放/件数/叠压顺序/缝线/包边/logo）③明确划出唯一允许改的东西（背景+光影+表面褶皱）。**判断口径：产品真实性要求高、或含 CJK logo、或纯色无纹理红利的品类，直接上编辑式，别再试生成式。** 代价与边界：**出图上限=拍摄质量上限**（原片糊/产品歪/死褶 AI 救不回来，要提升先改拍摄）；抚平表面褶皱会让 logo 文字略糊。
- **编辑式线里，"分析节点"是信息损耗点，该砍**（2026-07-24 V14 实锤）：V13 有 A1 产品DNA锁卡，把产品用文字描述一遍再注入下游。在生成式里它是必需的（模型只能靠文字知道产品长什么样），但在**编辑式里产品像素本来就在输入图里**，A1 反而变成损耗——实测它把 logo 文字转写错、把接近中性的淡色写成 `blush pink` 再被下游逐级放大成糖果粉。V14 直接砍掉 A1 与 IN2 logo特写，出图质量反而上去了。**推广口径：每加一个"把图翻译成文字"的节点，就多一次信息损耗；只在下游真的读不到原图时才需要它。**
- **场景/风格写死在提示词里 = 张张一个样，且改需求卡也没用**（2026-07-24 V14 复发，V9.2 老坑第二次）：GS 提示词里硬编码了「soft beige linen + dried flowers + ceramic dish」，跟需求卡的默认值一模一样，于是几轮出图全是同一个场景；就算改需求卡，提示词还在旁边喊同一句，两边打架。修法：**场景全部抽进数据层**——需求卡做成**场景池 + `Scene = N` 编号**（改数字即换场景，支持自定义优先），提示词改成"场景由需求卡定义，**不许默认**任何具体场景，需求卡说什么画什么"。这条与 V9.2「风格条款禁止写死单一模式」是同一条，**已复发一次，写新线时必须主动检查**：凡是提示词里出现具体的场景/道具/配色描述，都要问一句"这是不是该进数据层"。
- **★ Windows PowerShell 5.1 不能用来读写改含中文的 UTF-8 文件**（2026-07-24 实锤，当场毁掉两个提示词文件）：`Get-Content -Raw` 用系统 ANSI(GBK) 解码 UTF-8，中文当场变乱码，再 `Set-Content -Encoding utf8` 存回去就把乱码固化了，同时还加 BOM。我用它批量替换版本戳，A1 和 QA 两个提示词的中文全毁，只能 `git checkout` 回滚后用编辑器重做。**铁则：改文件内容一律用编辑器工具或 Python，PowerShell 只用来跑命令。** 这是同一类坑的第二次（第一次是 curl 内联 `-d` 发中文 JSON 变空 title），**根因都是 PowerShell 的编码处理**，已够格晋升知识库。
- **★ 护栏只写在质检侧＝只防不堵，必须在生成侧写对应的禁令**（2026-07-24 实锤，四宫格事故）：QA 的硬失败条款早就写了"出现拼贴/详情页排版=硬失败"，但四张 G 卡首跑**全部输出四宫格拼贴**——因为生成侧从来没有一句"禁止拼贴"。根因是 REQ2 里"本线固定4张+四摆法清单"连到每张 G 卡，被理解成"一张图里画四格"；这轮 G 卡又多了一张参考图，更助长排版倾向。修法两条：①数据卡（需求卡）里凡是"整条线共N张"这类说明，必须显式写"这是N个独立文件，每张卡只画自己那一种"②生成卡开头加硬指令（越靠前权重越高）。**推广口径：QA 能查出的每一类硬失败，都该在生成侧有一条对应的禁令；只在下游查=每次都要花钱重跑。**
- **给足真源后，生图模型能写出"真汉字但内容错"，不是只会乱码**（2026-07-24 修正 07-23 的过早结论）：07-23 判定"CJK logo 必糊成不可读假字、此路不通"。加了 IN3 色准真源 + IN2 logo 特写后复跑，出图的 logo **字形是真汉字**（"桑叶丝高棉色，建议更换。Biological clock"），S0 白底图甚至出过**完全正确**的一张。**修正后的口径：CJK logo 的失败模式是"写错字"而不是"写乱码"，取决于真源质量；用途允许字错（小尺寸装饰性）就能用，要字字准确仍须后期贴。** 教训：能力边界的结论要区分"完全做不到"和"做得到但不稳"，前者该换路，后者该改善输入。
- **★ 修图式补救有天花板，达不到就该止损换路，别逐轮补瑕疵**（2026-07-23 内裤线实锤，方法论教训）：为把真 logo 贴回 AI 生成图，一天内迭代四轮——①纯代码 alpha 混合（半透明边缘带进真源布色→白晕）②只擦墨迹不擦矩形（矩形硬擦把腰头缝线一起抹平）③墨色迁移+PCA 自动旋转（PCA 对"圆环+文字"估角错误，转完更歪，已移除）④PS 内容识别填充+正片叠底（内容识别在大片纯色布上会硬造缝线包边，把腿口白包边搬到 logo 下方）⑤印章+干净布覆盖+正片叠底。**每轮都补掉一个瑕疵又冒出新的，Joe 最终仍判"不行"。** 教训：这类"后期补救生成式缺陷"的活，**先判天花板再动手**——能到"远看没问题、放大有痕迹"就是上限，要求"放大也无痕"必须换路（真拍/手工PS），不该靠迭代硬凑。

- **场景参考是弱锚（影棚素背景）时，8张成品场景各自发明**（V9.2首跑实锤：G1画成白墙水泥地真实房间、G5画成影棚素背景，同一次运行）：无特征背景图锚不住场景，且当时C的风格支柱写死"真实场所/反影棚"与影棚场景冲突。修复（V9.2.1）：A3输出"场景类型+一句可逐字复用的场景句"，C按场景类型双模式切换且8组提示词verbatim复用同一场景句。教训：**风格条款禁止写死单一模式；跨图场景一致性=参考图+逐字同句双锁**。
- **未提供参考且无条款的可见部位（鞋）会每张自由发明**（V9.2首跑实锤：8张鞋款不一）。修复：C鞋类规则=有指定锁指定、无指定则选一个中性描述8组逐字重复；QA跨图一致性加"同一双鞋"。教训：**跨图一致性条款必须枚举所有可见部位，没参考的部位用"选定中性描述+逐字复用"模式兜底**。
- **需求卡文字与输入图矛盾时模型各画各的**（V9.2首跑实锤：REQ2身材写"健身强壮肌肉"但IN1是清瘦模特的头像三视图且无全身→8张身材漂移）。教训：**身材锚必须是全身模特图；需求卡文字只能强化图片事实，不能对抗图片**；输入图规范已写进DOC1（模特图须带体型、图4图5勿同图）。
- **小元素保真受输出像素预算硬限制**（V9.2两轮实测：全身图刺绣无一张对，提示词强化无效）：1K输出的全身构图里 2.5cm 刺绣只分到约20px，物理上画不对。修复路径=给像素而不是给措辞：①半身构图变体（胸区像素×3）②IN3 喂白底原片裁剪的真源细节图（make_detail_crop.py，无AI零幻觉）。教训：**保真问题先算像素账，再谈提示词**（元素在输出图中<40px 时属于物理不可画对区间）。★半身版效果待QA验证。
- **变体禁止复制规则引擎文件**：裂变半身版时把 C/QA 的构图硬编码全部移到 A3 分镜表（数据层），C/QA 变成分镜无关的单份引擎——否则护栏双份，下次修复只改一份，另一变体必回归。
- **verify_canvas.py 的项目id是位置参数**（2026-07-10实测）：`--project <id>` 会被 OPT_WITH_VALUE 当选项值吞掉导致 IndexError，正确用法 `verify_canvas.py [--spec xxx] [--variant x] <projectId>`。另：agent.json 在应用关闭后仍残留（端口拒连≠文件不在），apply 前先确认 LumaXFlow.exe 在跑（`Start-Process` 后约12秒网关才可 ping 通）。
- uv 管理的 Python 装包需 `--break-system-packages`（PEP 668 externally-managed）。
- **平台不因卡内容更新作废下游旧输出——热更新后必须从受影响组向下全链重跑**（2026-07-11 V12.1二测实锤，R14）："什么变化都没有"的真相=组②没重跑，G卡吃的还是旧编译文本（F1/CS输出带新版标记而SP1/C输出是旧格式，画布数据一锤定音）。修：①系统Agent输出第一行固定版本戳 ENGINE Vx.y，一眼识别旧货；②QA核对编译产物版本戳，落后即警告；③DOC重跑铁则。教训：**"改了卡=下游全部作废"要靠版本戳+流程铁则变成可见的，不能指望用户记得**。
- **用户拖图进画布会产生无连线的游离图片卡**（44卡 vs 蓝图37卡）：不影响运行（无连线不参与拓扑），核验脚本需容错无title卡。
- **多图输入的 LLM 质检节点不能按序号认图**（V9.1 首轮实测确认，已修复）：QA 一次收12张图，收图顺序与连线顺序不一致（8张图并发生成完成顺序随机/大模型多图计数错位），导致6个构图"硬失败"全是误报——QA 对内容的描述是准的，序号全错位。实锤证据：逐一调出8张 G 卡成品复核，张张符合自己的 Set。修复：QA 提示词改为"按内容认图"两步法（先按视觉特征区分参考图/成品图，再按构图特征匹配 Set 1-8），Set 缺失/重复本身即构图失败。教训：**凡是一次喂多张图给 LLM 判断的节点，一律内容认图，禁止序号认图**。
- **content-only 的单卡热更新是安全的**：apply 只发一张卡（ref+type+data.content）就能精准更新该卡提示词，不触碰连线顺序、不覆盖用户已编辑的其他卡。结构不变时优先用单卡 apply，不要全量重发。
- **白底平铺图无法传达弹力服装的上身松紧**（V9.0 实测确认）：Joe 在需求卡写"紧身贴身显肌肉"但出图宽松——因为版型归 A1 商品DNA管而 A1 只看平铺图且未连需求卡②。修复：版型上身要求做成硬指令字段，全链路 REQ2→A1→C→QA 贯通。教训：**凡是"图看不出来"的商品属性（松紧/弹力/垂感上身效果），必须给用户显式硬指令字段，不能指望模型从平铺图推断**。
- **用户心智：输入图=所见即所得**（V9.0 实测确认）：Joe 把"穿搭风格参考（mood图）"理解为"放搭配单品的地方"。教训：面向商家的工作流，输入图语义要做成"你给什么就穿什么"，AI 自主选品/配饰是负资产（他们有固定搭配），删掉反而更稳更省钱。
- **apply 更新已有项目有连线顺序陷阱**：apply 不隐式删除连线，删卡重连会让新连线追加到队尾，导致参考图槽位错位。结构性改动（删卡/改槽位）一律 apply 成新项目，不要原地升级。
- **素材A存在"连线槽位与提示词图号声明错位"**：TEXT8 连线序为图6/图3/图2，提示词却声明 Image1=商品/Image2=细节/Image3=风格；IMAGE4 同类错位。GPT-5.5 靠语义自愈所以"能跑"，但这是随机劣化源。V9.0 用构建器程序化保证连线序=前缀声明序。
- **素材A的生图卡从未真正挂姿势图**：所有 IMAGE 卡只有5张参考图，但提示词前缀声明了6张（Input Image 6 只存在于文字里）。V9.0 的 G1 真挂第6张姿势图，Set1用六图前缀、Set2-8用五图前缀。
- **平台引擎禁环**：QA→生图的级联反馈不能连成环（run 直接报错），必须做成向下的返修支线（R→RG）+ 单卡重跑。
- **构建脚本禁止写死机器路径**（2026-07-08 家机实锤，已修复）：build_lxf.py 的占位图源写死公司机 Temp 目录，家机重建直接失败。修复：占位图入库 `blueprints\assets\`，MEDIA_SRC 改相对蓝图路径。教训：**蓝图必须自包含，工具层只允许平台安装路径一个绝对路径且须是文件头配置常量**（已写入通用框架铁律12）。
- `.lxf` 是 Zip 包（PK头：canvas.json + manifest.json + media/images/）——文本 grep 搜不到卡内容，核验/取内容必须解包；`data` 字段是 JSON 字符串（不是对象）；导出格式与 apply 格式不同（导出：width/height/data字符串；apply：w/h/data对象且白名单 content/model/provider/size/resolution/quality，**不含 imageUrl**——apply 搭的图输入卡需手动放图）。
- Windows 控制台 GBK：py 脚本打印中文乱码，用 `py -X utf8` + `sys.stdout.reconfigure(encoding='utf-8')`。
- Git Bash 的 `/tmp` 与 Windows Python 路径不互通，临时文件用 scratchpad 绝对路径。

## 失败方案
- 无（本轮一次通过；curl 首次静默失败原因是把 node -e 内嵌在同一命令里取 port 失败，改为直接写死 agent.json 里的值即通）。

## 风险
- `run` 消耗余额：G1-G8 同层并发8张 high 质量图，瞬时消耗大；先跑组②检查提示词再跑组③。
- apply 的 data 出现白名单外字段会**整体拒绝**（不是静默丢弃）。
- 加密封装卡（`{"encrypted":true}`）不可读写，遇到只能连线使用。

## 规避策略
- 任何结构/提示词改动走 blueprints → 重跑 build/apply，保持蓝图为唯一真源。
- 新连线前先查 `E:\LumaX Flow\data\agent\docs\prompting.md` 槽位规则；生图卡入边数不得超过模型参考图槽位上限。
- 接口调用前先 GET /ping 与 /manifest 确认登录态与能力。
