# YANXINNA塑身衣独立站 · 踩坑记录

## 已解决的问题

### 1. 微信二维码弹窗定位问题
- 问题：弹窗被父容器 `fixed right-0 top-1/2` 限制，无法居中显示
- 解决：将弹窗移到父容器外面，使用 Fragment 包裹
- 文件：`components/ui/contact-fab.tsx`

### 2. 微信弹窗手机端适配
- 问题：手机端弹窗居中显示，看不到二维码
- 解决：手机端改为从右侧滑出，占 85% 宽度
- 关键代码：
```tsx
<div className="fixed right-0 top-0 h-full w-[85vw] max-w-[340px] bg-white shadow-2xl sm:static sm:mx-auto sm:h-auto sm:w-[340px] sm:rounded-xl">
```

### 3. 语法错误导致构建失败
- 问题：Fragment 标签 `<>` 没有正确闭合，div 标签嵌套错误
- 解决：修复 div 标签的嵌套结构，确保正确闭合
- 教训：修改 JSX 结构时要仔细检查标签闭合

### 4. Cloudflare Pages 不同步
- 问题：提交到 master 分支后，Cloudflare Pages 没有自动部署
- 原因：Cloudflare Pages 配置为监听 `feat/homepage-effects` 分支
- 解决：将 feat/homepage-effects 分支重置为 master 内容
- 教训：生产分支和开发分支要保持同步

### 5. 国旗 emoji 在 select 元素中不显示
- 问题：原生 `<select>` 元素不支持显示 emoji 国旗图标
- 解决：改用自定义下拉菜单组件
- 文件：`components/layout/locale-region-switcher.tsx`

### 6. select 元素不支持图片
- 问题：用户希望显示真实国旗图片，但 select 元素不支持
- 解决：使用自定义下拉菜单 + next/image 组件显示 `/images/flags/*.png`

### 7. PayPal 不支持 RUB，且 SDK 货币必须与订单一致
- 问题：PayPalScriptProvider 写死 `currency: "USD"`，下单却用地区货币（RUB/EUR/GBP），非 USD 报 currency mismatch；PayPal 根本不收 RUB，俄罗斯主市场无法付款
- 解决：统一按 USD 结算（`currency_code: "USD"`），展示价格用静态汇率换算（`lib/utils.ts` 的 `usdDisplayRates`），结账页加"以 USD 结算"多语言提示
- 教训：跨境收款先查支付渠道支持的货币清单，展示货币≠结算货币

### 8. 生产分支落后复发（踩坑 #4 二次发生）
- 问题：2026-07-13 发现 origin/feat/homepage-effects 落后本地 master 63 个提交，线上一直是旧版（产品都是旧的）
- 解决：`git branch -f feat/homepage-effects master` + `git push --force-with-lease`
- 教训：**每次收工推送 master 后必须同步强推 feat/homepage-effects**，两个动作绑定执行

### 9. ip-api.com 免费版仅 HTTP
- 问题：HTTPS 站点发 HTTP 请求被浏览器 mixed content 拦截，IP 地区检测永远失败
- 解决：换 `https://ipwho.is/`（免费支持 HTTPS，字段 country_code/success）
- 文件：`lib/region.ts`

### 10. BorderGlow 光晕导致手机端横向溢出
- 问题：edge-light 用负 inset 超出卡片 40px，手机端页面出现 24px 横向滚动
- 解决：外层 section 加 `overflow-x-clip`（不裁 y、不产生滚动容器，光晕 hover 效果保留）
- 文件：`components/home/factory-strengths.tsx`

### 11. 西里尔文导航更长，断点要按最长语言测
- 问题：导航加到 6 项后，俄语标签在 1024-1280 宽度溢出（英语没问题）
- 解决：桌面导航断点 md→xl（1280 起显示），中屏走汉堡菜单；nav 加 whitespace-nowrap，字距收窄 0.2em→0.12em
- 教训：多语言站改导航/按钮布局，必须切到俄语（最长）验证

### 12. 静态导出（output: export）没有后端，表单收不到数据
- 问题：样品申请表单原来只 console.log，询盘全部丢失；结账地址表单也没有去向
- 解决：询盘表单改 mailto 直达业务邮箱；结账地址塞进 PayPal 订单 shipping（SET_PROVIDED_ADDRESS），在 PayPal 后台可见
- 教训：静态站表单只有三条路——mailto、第三方表单服务、塞进支付订单

### 13. Tailwind 响应式字号类会覆盖 leading，导致大标题文字重叠
- 问题：`text-3xl leading-[1.15] sm:text-4xl md:text-[52px]` 这种写法，`sm:text-4xl` 自带 line-height（在 CSS 里排在 base 层 leading 之后，覆盖它），`md:text-[52px]` 任意值字号又不带行高 → 52px 字配 40px 行高，两行直接叠（Applications 页 hero、brand-story、首页 hero 都中招）
- 解决：用斜杠语法每个断点显式带行高：`text-3xl/[1.15] sm:text-4xl/[1.15] md:text-[52px]/[1.15]`（Tailwind 3.3+ 支持）
- 站内标准：Oswald 大写展示标题行高 1.15，Inter 粗体标题 1.2
- 教训：**凡是响应式改字号的标题，每个 text-* 断点都要带 /行高**，单独的 leading-[x] 会被后面断点的 text-Nxl 覆盖

### 14. dev server 运行时跑 npm run build 会损坏 .next 缓存
- 问题：dev 与 build 共写 `.next` 目录，build 会踩掉 dev 的 vendor-chunks（报 `Cannot find module './vendor-chunks/@paypal.js'`）；症状诡异——页面 SSR 输出正常、console 无错误，但客户端不 hydrate，所有交互失效（按钮无 React fiber）
- 解决：停 dev server → 删 `.next` → 重启 dev
- 教训：**跑 build 前先停 dev server**；遇到"页面能看但点不动、console 又干净"先查 hydration（元素上有无 __reactFiber 属性）和 dev server 日志

### 15. 多语言站的硬编码文案排查（2026-07-13 已清理）
- 问题三处：① ContactFab 悬浮框 4 个标签硬编码中文（询问/电子邮件/微信/顶部），俄语用户看到中文 ② ru-RU 文案值里残留中文（fabricsTitle "для高性能"，翻译时漏改）③ 手机端 <640px 顶栏语言切换器隐藏且抽屉菜单没有入口，手机用户无法切语言
- 解决：① 悬浮框+微信弹窗文案全部接入 copy 键 ② 修正俄语值 ③ 汉堡抽屉底部加 LocaleRegionSwitcher
- 排查命令：用 ripgrep `: "[^"]*\p{Han}` 扫 locale 值中的中文残留（Git Bash 自带 grep 的 [一-龥] 会对西里尔文误报，按字节匹配不可靠）
- 教训：新增 UI 文字一律走 copy 键；每个交互入口（含悬浮层、抽屉）要在最小屏宽下过一遍

### 16. ACF 新记录首次写值要优先使用 field key
- 问题：WP-CLI 创建新产品后，如果只用字段 name 调 `update_field()`，新记录尚无 `_field_name` 引用元数据时可能无法稳定建立字段引用。
- 解决：迁移器对所有顶层 ACF 字段使用版本化 `field_yx_v1_*` key 写入；产品编号仍作为幂等匹配键，所有导入记录保持草稿。
- 教训：ACF 批量导入“首次写入”与后台已有记录更新不同，迁移脚本应固定字段 key，并将 key 与代码注册的字段组一起版本控制。

### 17. OpenNext 在 Windows 能构建不等于生产运行已验证
- 问题：`opennextjs-cloudflare build` 在 Windows 成功生成 Worker，但工具仍明确警告 Windows 并非完全兼容，运行时可能出现不可预测问题。
- 解决：Windows 只作为本地编译证据；正式验收放到 Cloudflare staging 或 Linux CI，不能因为本地 bundle 生成就直接切生产。
- 教训：构建通过、适配器运行通过、真实云运行通过是三道不同门禁，要分别记录。

### 18. App Router 流式 404 的状态码与页面语义可能不同
- 问题：动态产品调用 `notFound()` 后，本地 Next App Router 流式响应可能仍是 HTTP 200，但会渲染 404 页面并注入 `noindex`。
- 处理：保留视觉 404 和 `noindex`；上线前在 staging 检查真实 Worker 响应和搜索引擎语义，不把本地 dev 状态码当成最终生产证据。
- 教训：动态路由 404 验收要同时检查页面内容、`noindex`、HTTP 状态和 CDN 行为。

### 19. 无 PHP/Docker 时可用 WordPress Playground 做后台兼容性预检
- 问题：Windows 机器没有 PHP CLI、Docker 或可用 WSL，无法直接打开自定义 WordPress 后台验证字段。
- 解决：使用官方 `@wp-playground/cli` 的 PHP WASM 运行时，自动挂载插件；本地预览用 Secure Custom Fields 验证 ACF 兼容字段组、Products 后台和只读 API。实际验证结果为字段页正常、产品与分类 API 均返回 200。
- 边界：Secure Custom Fields 只用于本地预览；正式环境仍按交付方案安装合法 ACF PRO，并在真实 PHP 主机重新跑语法、安全和 CRUD 验收。
- 教训：Playground 适合快速看后台和插件预检，但不能替代真实主机、授权插件、Webhook、WAF 和性能测试。

### 20. CMS 完整性校验"五语全必填"会让产品静默消失（2026-07-24 修复）
- 问题：`class-rest.php` 的 `map_product()` 在 `count($translations) !== 5` 时 `return null`，而 `translations()` 只要某语言缺任一必填字段就跳过该语言。迁移包 `products.json` 4 条产品只有 en-US/en-GB（`pending_locales` 明写 ru-RU/fr-FR/de-DE 待翻译）→ 后台点"发布"后状态显示已发布，公开 API 返回空，前台首页/商店/搜索全都没有它，后台零提示，只有服务器 error_log 一行英文。`localized_values()`（颜色名/参数/附件标签）有同样的全有或全无逻辑。
- 解决：新增 `fill_locale_fallback()`，缺失语言按 `ru-RU > en-US > 首个有内容的语言` 回退；完整性判定放宽为"至少一种语言齐全"；ACF 只保留俄语整组必填，其余四语可整组留空。提交 `05c7a3d`。
- **已在真实 WordPress 实测确认（2026-07-24，LocalWP + PHP 8.3.29 + WP 7.0.2）**：造一条只填 en-US 的产品并发布，只替换 `class-rest.php` 一个文件做 A/B——修复前 API 返回 `[]`（产品消失），修复后返回该产品且五语 name 全部回退为英语，颜色名同样回退。
- 教训：**CMS 的"数据不完整就不输出"策略必须配一个后台可见的提示**，否则运营侧永远查不出"发布了但看不见"。校验严于前端也是坑——前端 `localize.ts` 本来就写了 `?? translations["ru-RU"]` 回退，API 却比它严。

### 21. Windows Compress-Archive 打的 ZIP 条目名是反斜杠，WordPress 装不了
- 问题：PowerShell `Compress-Archive`（及 .NET Framework 的 `ZipFile.CreateFromDirectory`）用 `Path.DirectorySeparatorChar` 生成条目名，Windows 下得到 `plugin\includes\class-x.php`。WordPress 解压后会生成文件名里带 `\` 的怪文件，插件目录结构散架。
- 解决：手动建 `ZipArchive`，用 `CreateEntryFromFile($archive, $file, $正斜杠条目名, 'Optimal')` 逐个写入，打完用 `ZipFile::OpenRead` 列 `FullName` 确认是 `/`。
- 教训：**Windows 上打给 Linux/PHP 用的 ZIP，打完必须列一次条目名验证分隔符**；改了插件 PHP 记得重打 `wordpress/dist/*.zip`，那是个手工产物，没有构建脚本盯着它。

### 22. Secure Custom Fields 免费版含 repeater 和 gallery，ACF PRO 未必要买
- 背景：插件用了 repeater（sizes/colors/parameters/attachments/benefits）和 gallery，按 ACF 的传统划分这两个是 PRO 独占字段，交付文档因此把「有效 ACF PRO 许可证」写成硬前置。
- 实测（2026-07-24，LocalWP + WP 7.0.2）：从 wordpress.org 装免费的 **Secure Custom Fields 6.9.2**（WordPress 官方 fork），`acf_get_field_types()` 显示 repeater、gallery、group、relationship、color_picker、true_false、file、image、wysiwyg、number、select **11 种全部可用**；`group_yanxinna_products_v1` 字段组 13 个顶层字段完整注册；用 `update_field()` 写入 repeater/gallery/嵌套 group 后回读正常；公开 API 返回完整产品 JSON。
- 结论：本插件在 SCF 免费版下可完整运行，**ACF PRO 的 49 美元/年不是必须支出**。SCF 保留了 `acf_*` 函数名和 `field_*` key 兼容，插件代码零改动。
- 未定风险（标注为假设）：SCF 是 fork，长期可能与 ACF 上游分叉；正式站选哪个要作为一次明确决策记录，不要两个混装。
- 相关：本条推翻了踩坑 #19「SCF 只用于本地预览、正式仍需 ACF PRO」的边界结论，#19 当时是 Playground 里的表面观察，本次是真实 PHP 主机端到端验证。

### 23. LocalWP 是本机唯一可用的真实 PHP/WordPress 环境（无 PHP/Docker/WSL 发行版）
- 现状：本机 `php`、`docker`、`mysql` 均未安装，`wsl.exe` 存在但零发行版；`winget` 可用。
- 方案：`winget install Flywheel.Local` 装 LocalWP，建站时选 Custom → PHP 8.3.x + nginx + MySQL 8.0.35。PHP/MySQL 在建第一个站点时才下载。
- 命令行入口（绕开 GUI，可脚本化）：
  - PHP：`%APPDATA%\Local\lightning-services\php-8.3.29+1\bin\win64\php.exe`
  - php.ini（渲染后的，含 mysqli）：`%APPDATA%\Local\run\<siteId>\conf\php\php.ini`
  - WP-CLI：`%LOCALAPPDATA%\Programs\Local\resources\extraResources\bin\wp-cli\wp-cli.phar`
  - 调用：`php.exe -c <php.ini> wp-cli.phar --path=<站点>\app\public <命令>`
  - 站点根：`%USERPROFILE%\Local Sites\<站点名>\app\public`
- 两个坑：
  1. WP-CLI 的 `--fields=a,b,c` 在 PowerShell 里逗号会被拆成多个参数，报 `Too many positional arguments`——整个参数要加引号：`"--fields=name,status"`。复杂 PHP 片段不要用 `wp eval`，写成文件用 `wp eval-file`。
  2. **改 PHP 文件千万别用 PS 5.1 的 `Out-File -Encoding utf8`**，它加 BOM，PHP 开头多字节直接让插件失效（表现为 API 返回非 JSON）。要写 PHP 用 Git Bash 重定向或 `[System.IO.File]::WriteAllText` 配 `UTF8Encoding($false)`。
- 输出噪音：CLI 会刷 `Unable to load dynamic library 'php_imagick.dll'`，与业务无关，过滤掉即可。

### 24. WordPress WYSIWYG 字段返回 HTML，前端当字符串渲染出裸标签（2026-07-24 修复）
- 问题：产品详情页正文显示成字面量 `<p>A premium seamless bodysuit…</p>`，标签直接印在页面上。原因是 ACF/SCF 的 wysiwyg 字段返回 HTML，API 用 `wp_kses_post` 清洗后原样下发，而 `product-detail-client.tsx` 写的是 `<p>{product.description}</p>`，React 把 HTML 转义成文本。
- 为什么以前没发现：旧 `lib/data/products.ts` 的 description 是纯文本，接 CMS 才暴露。**只有真实 WordPress 数据能跑出这个 bug，fixture 测试和构建全都发现不了。**
- 解决：改成 `dangerouslySetInnerHTML`，容器加 `[&_p+p]:mt-4` 处理多段落间距。安全依据是 API 侧已过 `wp_kses_post` 白名单（WordPress 自己给文章正文用的标准）。提交 `614b97c`。
- 教训：**mock 数据换成 CMS 富文本字段时，要逐个检查渲染点是纯文本还是 HTML**；这类问题必须用真实数据在浏览器里看才能发现。

### 25. 交付文档里 import-products.php 的调用命令实际跑不通
- 问题：文档写 `wp eval-file import-products.php -- --media-base-url=https://…`，实跑报 `Error: Parameter errors: unknown --media-base-url parameter`。WP-CLI 会把 `--xxx` 当成自己的全局参数解析，`--` 分隔符对 `eval-file` 无效。
- 绕法（不改交付脚本）：写个壳脚本先赋值再 require：
```php
<?php
$args = array( '--media-base-url=http://站点/wp-content/uploads/migration-source/' );
require __DIR__ . '/import-products.php';
```
  壳脚本和 `import-products.php`、`products.json` 必须放同一目录（导入器用 `__DIR__` 找 JSON）。
- 图源准备：`products.json` 引用的 44 张图在生产分支 `public/products/`（CMS 分支已删）。不必另起静态服务器——直接拷进 WordPress 的 `wp-content/uploads/migration-source/`，`--media-base-url` 指向它即可，中文文件名的 sideload 实测正常。
- 实测结果：4 条产品全部导入为草稿，created 4 / updated 0 / failed 0。

### 26. 多语言站的"半本地化"死角：同一份数据两个页面显示不同语言
- 问题一（分类名）：商店页有 slug 到多语言的映射（`copy.categoryShapewear` 等），产品详情页却用 `titleCase(product.category)` 直接印原始 slug。同一个分类，商店页显示「Коррекция」，详情页面包屑显示「SHAPEWEAR」。详情页共四处中招：面包屑、标题上方标签、关联产品卡。
- 问题二（压缩等级）：`copy.compressionLevel` 只翻了**标签**「Уровень компрессии」，**值** Light/Medium/Firm 在五种语言下全显示英文，因为 copy 里根本没有这三个键。
- 解决：抽 `lib/category-labels.ts` 给商店页和详情页共用；locales.ts 补 `compressionLight/Medium/Firm` 三键 × 五语言。提交 `944221c`。
- 根因：WordPress 的 taxonomy term name 和 ACF select 的 enum 值都只有**一个值**，没有多语言位，这类字段的展示文案只能落在前端 copy。数据模型里凡是"单值 + 要展示给用户"的字段，都是这个死角的候选。
- 教训：**多语言站验收要按"同一条数据在所有出现它的页面上"横向对，不能只竖着看单页**；`titleCase(slug)` 这种写法在多语言站里几乎一定是漏翻的信号，值得全局 grep 一遍。

### 27. 浏览器控制台日志跨 dev server 重启不清空，会误判成真 bug
- 现象：改完组件后控制台报 `ReferenceError: titleCase is not defined`，停 dev server、删 `.next`、重启、硬刷新之后**报错依旧一字不差**，但源码里已经没有该引用、typecheck 通过、页面渲染完全正常。
- 判别方法：① 看栈——全在 `react-refresh` / `applyUpdate` / `scheduleRefresh` 里的，是热更新中间态，不是当前代码 ② 看 chunk 版本号——重启后 `webpack.js?v=...` 的值没变，说明读的是旧缓冲区 ③ **决定性做法：开一个新标签页加载同一地址**，新标签的控制台缓冲区是空的，那里干净就是真干净。
- 教训：编辑期间先删 import 再改用法，中间必然出现一次引用未定义，HMR 会把它记进控制台；**判断"改完有没有错"要用新标签页，不要信同一标签的历史日志**。

### 28. OpenNext 不配缓存后端，Cloudflare 上完全不缓存（2026-07-24 修复）
- 问题：`open-next.config.ts` 只写了 `defineCloudflareConfig()`，没配 `incrementalCache` 和 `tagCache`。OpenNext 在 Cloudflare 上因此**完全不缓存**——`lib/wordpress/client.ts` 里的 `next: { revalidate: 300, tags }` 静默失效，每个访客的每次页面访问都直接回源打 WordPress，`/api/revalidate` 刷的是不存在的缓存，整套 Webhook 是空转。
- 发现方法（关键）：**绕过 Webhook 直接改数据库 meta**（`wp post meta update`，不触发 `save_post`），然后立刻请求 Worker。如果新值马上出现，就说明根本没缓存。用正常的"后台保存 → 看前台变了"验不出来，因为两条路径都会变。
- 解决：`incrementalCache: kvIncrementalCache` + `tagCache: kvTagCache`（都用 KV，不引入 D1，少一种资源）；`wrangler.jsonc` 加绑定 `NEXT_INC_CACHE_KV`、`NEXT_TAG_CACHE_KV`。本地 `wrangler dev` 用 miniflare 模拟，占位 id 就能跑；部署前用 `npx wrangler kv namespace create` 换真实 id。提交 `4b0d8c7`。
- 三步验证法（已通过）：① 请求一次建立缓存 ② 绕过 Webhook 改库，再请求应**仍返回旧值** ③ 触发保存发 Webhook，再请求应**返回新值**。
- 教训：**缓存"配了没生效"和"没配"外观完全一样**，必须用绕过失效路径的手段主动证伪。Next 的 `revalidate`/`tags` 只是声明，真正生效依赖部署适配器有缓存后端。

### 29. WordPress Webhook 的目标 URL 有三重硬限制，失败只有一行日志
- 现象：本地 Worker 地址 `http://localhost:8787` 配进 `YANXINNA_FRONTEND_URL` 后，Webhook 完全不发，后台无任何提示，只有 PHP 错误日志一行 `[YANXINNA Headless Products] Cache refresh skipped: invalid frontend URL.`
- 根因：`wp_http_validate_url()`（`wp-includes/http.php`）三道拦截——① 拒绝 loopback 和私网 IP（127./10./0./172.16-31./192.168.），可用 `http_request_host_is_external` 过滤器放行 ② **只允许端口 80 / 443 / 8080**，其他端口需 `http_allowed_safe_ports` 过滤器放行 ③ 域名必须能 `gethostbyname` 解析。
- 生产影响：Cloudflare Worker 的 `*.workers.dev` 是 HTTPS 443，天然通过。但**若前端地址用了非标准端口，Webhook 会静默失效**。
- 本地验证办法：在测试站 `wp-content/mu-plugins/` 放一个只放行 loopback + 8787 端口的文件（**绝不能进仓库或公网站点**）：
```php
add_filter( 'http_request_host_is_external', '__return_true' );
add_filter( 'http_allowed_safe_ports', function ( $ports ) { $ports[] = 8787; return $ports; } );
```
- 不加这个也能验一半：用 `pre_http_request` 过滤器截获出站请求，检查 URL、方法、`x-yanxinna-secret` 头和 body 是否正确，请求不会真的发出去。

### 30. PowerShell 生成的密钥带 BOM，导致 HTTP 鉴权莫名 401
- 问题：用 `Out-File -Encoding utf8 -NoNewline` 写的 64 位密钥文件，实际带 3 字节 BOM（`ef bb bf`）。这个文件被灌进 `.env.local`、`.dev.vars` 和 curl 请求头后，`/api/revalidate` 用正确密钥仍返回 401。
- 判别：`wc -c` 或 `${#VAR}` 得到 67 而不是 64；`od -An -tx1 -N3 文件` 头三字节是 `ef bb bf`。
- 解决：`sed -i '1s/^\xEF\xBB\xBF//' 文件` 去 BOM 后重新灌入各处配置。
- 教训：这是踩坑 #23 第二条的同一根因换了个场景。**PS 5.1 不要用 `Out-File -Encoding utf8` 生成任何会被程序逐字节比较的内容**（密钥、token、PHP 文件）。要么用 Git Bash 重定向，要么 `[System.IO.File]::WriteAllText($path,$s,(New-Object System.Text.UTF8Encoding($false)))`。

### 33. PowerShell 管道灌 `wrangler secret put`，把 `\r\n` 一起存进密钥

### 37. 阿里云内网 DNS 会缓存旧 NS 的否定应答，Webhook 静默失效
- 现象：域名换 NS 到 Cloudflare、主域绑好 Worker 后，公网（`8.8.8.8`、`223.5.5.5`、Cloudflare 权威）都能查到 A 记录，**唯独服务器自己解析不出来**。表现是 `wp_http_validate_url()` 返回 `false`、Webhook 只在日志留一行 `Cache refresh skipped: invalid frontend URL.`（踩坑 #29 第③条那个条件）。
- 判别（服务器上，先 `sudo yum install -y bind-utils`）：
```bash
getent ahostsv4 yanxinna.com                      # 空 = A 记录解析不出来
php -r 'var_dump(gethostbyname("yanxinna.com"));'  # 返回域名本身 = 失败
dig +noall +answer +authority A yanxinna.com @100.100.2.136   # 看它返回谁的 SOA
```
- 根因：阿里云内网 DNS `100.100.2.136` 里还存着**旧 NS（`dns25.hichina.com`）的否定应答**，否定缓存 TTL 600 秒起，而且实测等过一轮也没自动更新到 Cloudflare 的委派。
- 解决：把解析交给阿里自家公共 DNS（同生态、同地域，不引入新依赖）。**NetworkManager 管着 `/etc/resolv.conf`，只改文件重启会丢**，两处都要写：
```bash
sudo nmcli connection modify "System eth0" ipv4.dns "223.5.5.5 223.6.6.6 100.100.2.136" ipv4.ignore-auto-dns yes
# 再直接写 /etc/resolv.conf 让它立刻生效（nmcli modify 不重启连接就不会应用，
# 而 nmcli connection up 会断网，SSH 会掉）
```
- 连带一条：**阿里云轻量没有 IPv6 出口，但 Cloudflare 的 AAAA 记录照样能解析到**，于是出站请求先试 IPv6 再退回 IPv4，白等一轮。修法是让 `getaddrinfo` 优先 IPv4：往 `/etc/gai.conf` 追加 `precedence ::ffff:0:0/96  100`。
- 验证：2026-08-03，改完 `gethostbyname` 返回 `104.21.75.85`、服务器 `curl https://yanxinna.com` 200、`wp_http_validate_url` 通过、Webhook 恢复。

### 38. Cloudflare KV 是最终一致性，内容更新「约 1 分钟」才是正常值
- 背景：07-30 staging 实测「产品切 draft 后 8 秒前台跟上」，一度被当成基准。2026-08-03 正式站复测，实际是 **50–150 秒之间**才生效。
- 根因：OpenNext 的 tag 缓存落在 Cloudflare **KV**，KV 是最终一致性存储，写入向各边缘节点传播**最长 60 秒**。8 秒是当时恰好命中同一个节点的运气。
- 排查顺序（别一上来就怀疑 Webhook）：先直接打 `/api/revalidate`，正确密钥应 200、错误密钥应 401 —— 这两条过了就说明密钥和端点都没问题，剩下的等待属正常传播。
- 结论：**验收标准写「60 秒内更新」，不要写「10 秒内」**，否则会把正常表现当故障排查。
- 验证：2026-08-03 正式站，切 draft 后 t+50s 仍在、t+150s 消失；切回 publish 后约 70 秒恢复。

- 验证：2026-08-04，`wp_mail` 在 wp-cli 和 php-fpm 两种上下文都返回 true，耗时 1.3–2.5 秒。

### 43. `wp_mail` 失败只给一个 `false`，不接 `wp_mail_failed` 就永远查不出原因

- 现象：2026-08-04 接通 SMTP 后，询盘 ID 63 在 php-fpm 上下文发信失败，同一天另外 4 次（1 次询盘 + 3 次密码重置）全部成功，wp-cli 上下文一直正常。SELinux 是 `Disabled`，已排除。**原因至今没复现**。
- 教训：`wp_mail()` 只返回 bool，PHPMailer 的真实报错在 `wp_mail_failed` 这个 action 里，不接就是黑盒。**接通 SMTP 的同时就要把这个钩子接上**，别等出问题再补 —— 出问题时那次的报错已经没了。
```php
add_action( 'wp_mail_failed', function ( $error ) {
    error_log( 'YANXINNA: wp_mail failed — ' . $error->get_error_message() );
} );
```
- 日志落在 `/www/wwwlogs/cms.yanxinna.com.error.log`（php-fpm 的 stderr 被 nginx 收走，不在 `/www/server/php/83/var/log/`）。查：
```bash
sudo grep -h "YANXINNA:" /www/wwwlogs/cms.yanxinna.com.error.log | tail
```
- 配套处理：询盘提醒失败后重试一次（询盘本身已落库不会丢，丢的只是提醒，但商家不登后台发现不了）。
- ★ **测发信别只看 `wp_mail` 返回 true** —— 那只代表对方 SMTP 服务器收下了，不代表投递成功。中国移动 139 发往 Gmail 可能被丢弃或进垃圾箱，**必须去收件箱和垃圾箱各确认一次**才算通。

### 44. 宝塔面板在这台服务器上外网进不去，别把改配置的路子押在它身上

- 现象：`http://47.243.151.206:8888` 外网不可达（curl 返回 `000`）。面板本身是跑着的（`Bt-Panel already running`），端口 8888，安全入口为空，无 IP 限制。
- 根因：**阿里云轻量的防火墙只放行 22 / 80 / 443**，8888 没开。
- 别为了改个配置去公网放行 8888（等于把面板暴露给全网扫描器）。改 wp-config 一律用：
```bash
sudo -u www /usr/local/bin/wp --path=/www/wwwroot/wordpress config set <常量名> <值> --type=constant
# 数字值加 --raw，否则会被写成字符串
```
- 服务器上**没装 nano，只有 vim/vi**；`zip` 也没装，但 `python3` 有。
- ★ **`admin` 用户密码是锁死状态（`passwd -S admin` 显示 `Password locked`）**，只能用密钥登录。阿里云控制台的「远程连接」里**只能用 root + 实例密码**进，这是密钥丢失后唯一的保命路径 —— 实例密码忘了就在控制台「重置密码」。
- 验证：2026-08-04 全部实测。

### 45. 自定义 CPT 忘了写 `capability_type`，受限角色就看不到那个菜单

- 现象：2026-08-04 准备建商家账号前抽查，发现 `yx_product_manager` 角色**看不到「询盘」菜单** —— 而询盘系统的全部意义就是让商家看到线索，这是交接必炸的点。
- 根因：`yx_inquiry` 注册时只写了 `capabilities => array('create_posts' => 'do_not_allow')` 和 `map_meta_cap => true`，**没写 `capability_type`**，于是默认退回 `'post'`。看这个 CPT 就需要通用的 `edit_posts`，而产品经理角色（刻意做的最小权限）没有它。产品 CPT 反而没事，因为它当初写了 `capability_type => array('yx_product','yx_products')`。
- ★ **别用「给角色加 edit_posts」来解决** —— 那等于顺带开放整个 WordPress 的文章和页面，最小权限角色就白做了。正解是给 CPT 独立权限类型 + 把对应权限装给角色。
- ★ **管理员也必须一起装**：换成独立权限类型后，`administrator` 自带的 `edit_posts` 同样看不到这个 CPT 了。只给新角色装、忘了管理员，等于把自己也锁在外面。
- 一分钟自查（任何自定义 CPT 都能用）：
```bash
wp eval '$pt=get_post_type_object("<CPT名>"); echo $pt->cap->edit_posts."\n"; foreach(["<角色>","administrator"] as $r){ printf("%s: %s\n",$r,get_role($r)->has_cap($pt->cap->edit_posts)?"有":"没有"); }'
```
  输出的权限名如果是裸的 `edit_posts`，就说明 `capability_type` 漏了。
- ★ **改完必须手动重装角色**：`install_roles()` 只挂在 `register_activation_hook` 上，**覆盖插件文件不会触发它**。跑 `wp eval 'YANXINNA_Headless_Content::install_roles();'`，不跑的话权限改动完全不生效。
- 验证：2026-08-04，修完实测两个角色都能看/删询盘、后台新建仍被 `do_not_allow` 挡住、产品经理仍无 `edit_posts`/`edit_pages`/`manage_options`/`edit_users`/`install_plugins`；询盘写入不受影响（`wp_insert_post` 本来就不校验权限）。

### 46. `wp db export` 在宝塔机器上要加 `--socket`，输出目录还得 www 写得进去

两个坑连着踩，都在同一条命令上：

- **socket 路径**：报 `Can't connect to local MySQL server through socket '/var/lib/mysql/mysql.sock' (2)`。宝塔把 MariaDB 的 socket 放在 **`/tmp/mysql.sock`**，而 `mariadb-dump` 编译时的默认值是 `/var/lib/mysql/mysql.sock`，且不读 `my.cnf` 里 `[mysqld]` 段的 `socket`。WordPress 自己连得上是因为 PHP 那条路径另算——**"网站好好的"不代表 mysqldump 连得上**。
  - 查真实位置：`sudo ss -lx | grep mysql` 或 `sudo grep -rh "^socket" /etc/my.cnf /etc/my.cnf.d/*.cnf`
  - 解法：`wp db export <文件> --socket=/tmp/mysql.sock`（wp-cli 会把这个参数透传给 mysqldump）
- **输出目录权限**：报 `Can't create/write to file ... (Errcode: 13 "Permission denied")`。命令是 `sudo -u www wp ...`，所以真正写文件的是 `www` 用户，输出目录必须它写得进去 —— `mkdir /tmp/bk && chmod 777 /tmp/bk`，导完再 `chown` 回来。
- ★ **导完一定要数一下再走**：`grep -c "INSERT INTO"` 和媒体文件数。第一次失败时产出的是一个 **36 字节的 .gz**，不校验就当备份收着了，等要恢复才发现是空的。
- 完整可复用脚本：`E:\Backups\yanxinna-cms\backup.sh`（含以上全部规避）。
- 验证：2026-08-04，脚本端到端跑通，产出数据库 9 条 INSERT、媒体 184 个，压缩包校验通过。

## 经验总结
1. 弹窗组件：不要被父容器的定位限制，要用 Fragment 移到外面
2. 手机端适配：弹窗类组件要考虑从边缘滑出的交互方式
3. JSX 语法：修改结构后要仔细检查标签闭合
4. 部署分支：确保开发分支和生产分支同步
5. 自定义组件：原生 HTML 元素功能有限时，考虑自定义实现
6. 多语言同步：修改文案时要同步更新所有5种语言版本（ru-RU、en-US、en-GB、fr-FR、de-DE）
7. 图片路径：新图片放 `/public/images/` 目录，使用 next/image 组件加载
8. CMS 迁移：只导入草稿；字段、翻译、媒体、API 和缓存刷新全部在 staging 验证后再发布
