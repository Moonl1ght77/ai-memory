# 小红书运营获客系统 · 踩坑记录

## 已确认问题

### MediaCrawler 拷贝里带着别人的登录态（2026-08-05 发现，✅ 2026-08-09 已清除）

`E:\Tools\小红书爬虫` 是 Joe 从**老板电脑**拷下来的，里面 `browser_data\xhs_user_data_dir\` 有 **46MB 的完整 Chrome 登录会话**。

**风险**：如果那是老板的小红书账号，Joe 跑这个项目 = 以老板身份在小红书上活动，抓取记录和痕迹都算在对方头上。

**处理**：2026-08-09 在公司机把 `browser_data\` 整个删掉了（Joe 确认）。项目配置是 `LOGIN_TYPE = "qrcode"`，下次跑会重新弹二维码，用新号扫。

**通用教训**：从别人电脑拷来的爬虫/自动化项目，**先查有没有 `browser_data` / `user_data_dir` / `.env` / cookie 文件**，别带着别人的身份开跑。

**注**：AI 没有翻过那个目录里的内容——别人的登录凭据不碰。

### MediaCrawler 明文禁止商业用途（2026-08-05 查实）

仓库条款限定「仅供学习和参考之用」，并写明不得用于非学习、非研究的商业行为。

**这一条和本项目直接冲突**——2026-08-05 Joe 明确终局是**系统交给商家、商家自己操作**。那一刻就是正面违反条款，没有解释空间。

**连带的死结**：换掉 MediaCrawler 就没有正文全文和评论（Agent Reach 只有标题/点赞/链接），而痛点、热门选题、内容趋势三项核心产出全靠正文和评论。**所以「合规的数据源能不能拿到正文和评论」是产品化的地基问题，不解决就不能做界面。**

第一版是 Joe 内部自用、不对外分发，暂时擦边不冲突。

对比：Agent Reach 和 google-maps-scraper 都是 MIT，无使用限制。**MediaCrawler 是三个工具里唯一明文排除商业使用的。**

Joe 已知悉此条款，用不用由他定。但**做产品化决策前必须重新过一遍这条**，别到上线才发现。

### MediaCrawler 免费版没有 AI 集成

AI agent 集成（OpenClaw / Claude Code / Cursor）是 **Pro 付费版**功能。开源版只有命令行和网页界面。

**意味着**：MediaCrawler 这条路是 **Joe 自己跑命令**，跑完把结果文件给 AI 处理，不是 AI 直接调用。设计流程时要把这个人工环节算进去。

### MediaCrawler 故意不采集任何个人信息（2026-08-05 查实，硬约束）

`tools\user_hash.py` 开头写明：教学版「爬取结果中不保留任何可定位到真人的用户个人信息（用户 ID、IP 归属地、头像、主页链接、签名、性别等一律不采集；昵称保留但做中间脱敏）」。

实际效果：`nickname` 存成 `W***I`，`user_id` 被 sha256 截断成 `creator_hash`。

**后果（决定了产品形态）**：
- 能认出「这几篇是同一个人发的」，但**拿不到他主页，联系不上任何一个人**
- 评论里问「哪买」「有链接吗」的是真线索，但点不到人
- 所以本项目获客定位为**「找场子不找人」**——产出客户密集出现的位置，不提取个人
- 要做主动私信式获客，得走小红书官方业务工具（蒲公英/商业后台），是另一条路

**不要试图绕过它**（改代码提取个人信息）：既踩「不改第三方仓库」的禁区，也是绕开人家刻意做的防骚扰设计。

### 默认按热度排序，抓回来的是跨年爆款集合（2026-08-05 查实）

`config\xhs_config.py` 里 `SORT_TYPE = "popularity_descending"`。8月4号那轮抓的 10 条笔记，发布时间从 2024-11 横跨到 2026-07。

**后果**：**用这个抓法算不出「内容趋势」**。两年的爆款集合回答不了「最近大家在发什么」。8月4号那份报告里也确实没有趋势这一节。

**规避**：同一批种子词跑两轮——`popularity_descending`（热度榜，看什么长期能打）+ `time_descending`（最新榜，看近期在发什么），两榜对比才有趋势。

**排序没有命令行参数**（`cmd_arg\arg.py` 里没有 `--sort_type`），只能改配置文件——那是禁区。

**解法（✅ 2026-08-11 首轮实跑验证成功）**：`脚本\爬虫启动器.py` —— 先 `sys.path.insert` 爬虫目录、`import config` 覆盖 `config.SORT_TYPE`，再 `runpy.run_path` 调它的 `main.py`，仓库零修改。
用法：`python 脚本\爬虫启动器.py 最新榜 --platform xhs --lt qrcode …`（第一个参数「热度榜/最新榜」，其余原样传给爬虫）。
**验证证据**：最新榜抓回的 119 篇发布时间只有 2026-07~08，热度榜 110 篇跨 2022-04~2026-08。产出用 `--save_data_path` 落到本项目，爬虫仓库里没留任何东西。

### 评论抓取已实测通过；但评论数据里噪音占大头（2026-08-05 量过）

`E:\Tools\小红书爬虫\runs\knitwear_test_20260804_01\` 里有完整跑通记录：10 条笔记 + **187 条评论** + 分析报告.md + 一张长图。评论字段带 `content` `like_count` `sub_comment_count` `parent_comment_id`。

**实测的数据质量（这个数字用来定样本量）**：
- 187 条评论平均 13.8 字
- 去表情后 ≤4 字的 36 条（19%，无信息量）
- ≥15 字真有信息量的只有 **35 条（19%）**
- 最长的几条里有两条是**同行在评论区打广告**（"现货已备齐，主理人/设计师/采购负责人带名片滴滴"）——这不是噪音是情报，报告里单独成栏叫「同行截流」

**推论**：想让痛点占比有意义，评论得上千条量级。所以定为每种排序 30 条笔记 × 每篇 20 评论。

**另一个推论**：187 条 × 13.8 字 ≈ 2600 字，AI 一口吃得下。**"上下文塞不下所以要用规则匹配分类"这个顾虑不成立**，1000 条评论也才 1.4 万字。

### 抓取条数是「每个种子词」的上限，且长尾词根本搜不满（2026-08-10 实测）

`core.py` 的 `collected_count` 在关键词循环**内部**重置。所以 `CRAWLER_MAX_NOTES_COUNT = 15` 的意思是**每个种子词最多 15 篇**，不是一共 15 篇。

8/4 那轮实测（配置上限 15，3 个种子词）：

| 种子词 | 实际搜到 |
|---|---|
| `针织面料 男装` | 4 篇 |
| `针织面料 日常通勤` | 3 篇 |
| `针织面料 商务` | 3 篇 |

**搜到 3-4 篇就 `has_more=False` 了，远不到上限 15。**

**两条推论**：
1. **总量 = 种子词数 × 上限 × 排序数**。3-8 个词 × 30 × 2 = 180-480 篇，不是原以为的 60 篇。**「每种排序 30 条」这个说法本身就是错的**
2. **种子词越长尾，结果越少**。实际条数由搜索结果决定，不由配置决定。勾选表里必须留至少一个宽词保量

### 评论只能抓到每篇前 20 条，总覆盖率 13%（2026-08-10 实测）

8/4 那 10 篇笔记在平台上共 **1424 条**评论，实际抓到 **187 条**。**每篇死死抓 20 条，不管平台上有多少。**

| 笔记 | 平台评论数 | 抓到 | 覆盖率 |
|---|---|---|---|
| 视频（2.4万赞爆款） | 939 | 20 | **2%** |
| 视频 | 114 | 20 | 18% |
| 图文 | 44 | 20 | 45% |
| 图文 | 7 | 7 | 100% |

**成因**：`CRAWLER_MAX_COMMENTS_COUNT_SINGLENOTES = 10`，但按页取、页大小 20，取够 10 就停——整页已经拿回来了。**想抓更多得调到 21 以上才会翻第二页。**
（之前记的「上限 20/篇」结论对，成因记错了。）

**影响**：痛点占比的原料是「每篇前 20 条」，不是随机样本，且**越爆的笔记越不代表**。报告里任何占比都必须标注这个偏差。

**另外**：`ENABLE_GET_SUB_COMMENTS = False`，实测 187 条**全是顶级评论、0 条回复**。楼中楼里的追问拿不到。

### 新建的 GitHub 仓库默认公开，建完必须验证（2026-08-05 实际踩到）

2026-08-05 建 `xhs-growth-system` 时，明确要求选 Private，实际建出来是 **Public**。第一次推送后才发现，`需求文档.md` 里的许可证冲突措辞、老板登录态那段、整套方法论全部短暂公开过。

**验证方法（不用登录、不用 gh）**：匿名调 GitHub API，Public 返回 200，Private 返回 404。

```powershell
try { $r=Invoke-RestMethod -Uri 'https://api.github.com/repos/<用户名>/<仓库名>' -Headers @{'User-Agent'='check'} -ErrorAction Stop; "公开! private = $($r.private)" } catch { "已私有（匿名 404）" }
```

**规矩**：**以后每次新建 GitHub 仓库并首次推送后，立刻跑这条验证，不要假设建的时候选对了。**
（此条具备跨项目复用价值，等第二次验证后可考虑晋升知识库）

**改法**：仓库 Settings → 最底部 Danger Zone → Change repository visibility → Make private。改完推送凭据依然有效，不用重新配。

### 爬虫 venv 是 uv 壳，底层 Python 被清掉会假死（2026-08-10 实际踩到，已修复）

跑 `.venv\Scripts\python.exe` 报 `uv trampoline failed to spawn Python child process: entity not found`。原因：`.venv` 是 uv 建的，python.exe 只是个壳，指向 `C:\Users\Administrator\AppData\Roaming\uv\python\cpython-3.11-...`——那个目录整个没了（不知何时被清理）。

**修复（不用重建 venv）**：`uv python install 3.11`，9 秒装回 3.11.15，venv 原地复活。

**教训**：uv 系 venv 报「找不到实体」先查 `pyvenv.cfg` 里的 `home` 路径在不在，别急着重装依赖。

### 扫码窗口在登录完成前被关，爬虫直接退出（2026-08-10 踩到）

弹出的浏览器窗口是爬虫自己的会话，扫码完成前关掉会 `TargetClosedError` 退程序。跟 Joe 交代时要说清「窗口别关，扫完放着」。另外登录态成功后存 `browser_data\`，之后不再弹码。

### cookie 免扫码方案会踢掉 Joe 浏览器的登录（2026-08-11 实际踩到，已放弃）

为躲扫码，写了启动器读 `登录cookie.txt`（只放 `web_session` 值）走 `--lt cookie`。结果：
1. 爬虫确实不弹码了，但 `pong` 检查返回 `Login state result: False`——单靠 `web_session` 不够（小红书还要 `a1`/`webId` 配合）
2. **更严重**：同一会话两处使用，小红书直接作废它——**Joe 自己的 Chrome 当场掉登录**，弹出手机号登录框

**结论：cookie 方案不用。** 定为——爬虫走扫码（Joe 用自己账号自己扫，10 秒），浏览器该怎么用怎么用，两边互不干扰。启动器保留 cookie 分支代码，但**项目里不要放 cookie 文件**（放了就会走那条路）。

### 用小白鼠号跑爬虫，流程会卡死在「扫码的人不在」（2026-08-11 定案改用 Joe 自己账号）

8/6 定用新注册小白鼠号隔离风险，实跑发现两个反效果：
1. **新号风控更狠**：8/10 晚扫码成功后 **6 分钟**就被掐会话（日志「登录已过期」），50 篇抓完就断
2. **流程不可用**：号在商家手机上，人不在就跑不了。Joe 直接打了零分——**这是首轮实跑最有价值的发现：依赖别人手机的流程等于死流程**

**改法**：用 Joe 自己的小红书账号跑。抓取量（一轮百来篇）比他平时刷小红书还少，老号有正常痕迹、风控更宽松，会话活得久。**流程可用性 > 理论上的账号隔离。**

### 分层词表是行业知识，换行业会静默失效（2026-08-11 系统测试发现并修复）

首轮做的 B端/C端分层，词表全是从面料数据里提取的（克重/门幅/剪版/中大）。**拿别行业的真实口气压测，9 个用例误判 4 个，全是「B端被漏判成无信号」**：

| 行业 | 漏判的评论 |
|---|---|
| 塑身衣 | 「无缝针织代工接吗，贴牌」 |
| 宠物用品 | 「这款猫爬架能定制LOGO吗，一次订500个」「有没有代发，我开宠物店的」 |
| 美妆 | 「可以代工吗，有ODM方案吗」 |

**危险在方向**：漏判会让画像验证占比偏低，报告把「行业词表不匹配」误报成「种子词选错了」，人会去改一个没错的东西。

**修法（已实施，`脚本\出就绪包.py`）**：词表拆两层 —— **通用 B端层**（代工/贴牌/OEM/ODM/起订/代发/定制/供货/厂家/源头/拿货/货源…，跨行业成立，换行业不用改）+ **行业专属层**（`B_WORDS_INDUSTRY`，换行业必须换）+ **批量意图正则**（「一次订500个」这类，比任何词表都硬）。补完 9/9 命中。
脚本文件末尾写了「换行业指引」，列明换行业要改哪 3 处、不用改哪 3 处。

**新行业的正确做法**：第一轮先只靠通用层跑，从抓回的评论里挑该行业高频术语，再填进行业层和词库 —— 和「词库沉淀式」同一个思路，只存有数据背书的词。

### 抓回的笔记 `desc`/`title` 可能是 null 不是空串（2026-08-11 系统测试踩到）

`n.get("desc", "")` 拿到的是 `None`，喂给正则直接 `TypeError` 崩掉。**视频笔记经常没有正文**，这在真实数据里迟早会踩（首轮侥幸没遇到）。
**修法**：统一用 `text_of(d, *keys)` 取文本（`str(d.get(k) or "")`），已覆盖 desc/title/content/ip_location。脏数据用例已写进自检防退化。

## 风险

- **合并两个爬虫工具的代码**——评估过，不要做。一个 Go 程序 + 一个 Python 程序 + 一堆 npm 工具，架构完全不同，合起来是几周工程量；且两边都在活跃开发，合并后每次上游更新都要手动并，**Joe 不写代码维护不了**。正确做法是加一层路由规则 + 统一输出格式，不动底层代码
- **凭空写一份行业关键词库**——Joe 2026-08-05 选了「建库」，但澄清后定为**沉淀式**：只存有真实数据背书的词。凭 AI 常识写满几个行业的词表，本质是把常识存成文件，不知道哪个词真有流量、哪个是死词
- **小样本冒充大数据**——每种排序 30 条 = 两轮共 60 篇笔记。**这不是大数据**。任何画像占比、市场占比类结论都必须标注「方向性判断，不代表平台占比」。8月4号那份报告自己写了这句，要保留这个习惯

## 规避策略

- 需求文档出来之前不写代码
- 涉及第三方仓库拷贝，只读不改；系统本体代码写在 `E:\Projects\小红书运营获客系统`
- 三个工具的输出格式各不相同（Agent Reach 出 JSON、MediaCrawler 出 JSONL、谷歌地图抓取器出 CSV），统一转成中文表头 CSV 给 Joe 看。转换脚本已有基础版：`~\.local\bin\gmaps-enrich.js`
