## 已确认问题
- 服务器只有 HTTP（80），WebFetch 类工具会强制升 HTTPS 导致连不上；抓页面用 `curl http://43.132.168.36/...`（2026-08-13 验证）
- nginx 对 `/operator/*` 的 POST 返回 404（GET 正常）——控制台网页里所有"新建/保存"操作应该都是坏的，绕法：服务器上直打 `127.0.0.1:8787`。已列入待同事修（2026-08-13 登记能力时发现）
- apimart 对 gpt-5.6 系列聊天模型**无视 stream:false 强制 SSE 流式返回**，标准 JSON 解析直接炸。修法：检测 `data:` 开头就按 SSE 拼接（zexin_print_agent.py chat() 已带兜底，2026-08-13 实测）
- apimart 高峰期**瞬时 401/500 抽风**（后端过载报"Too many connections"，连鉴权都乱拒），几分钟后自愈。症状：之前好好的密钥突然 401，同刻探针再测又 200。平台侧重试是7秒内连打3发（无退避），全撞抽风窗必全灭。已修：zexin_print_agent 对 401/429/5xx 做 5s/10s 退避重试两次（2026-08-13 实测）
- **飞书消息被劫走：同事本机实例和服务器连同一个飞书应用**（websocket 双连接，消息随机分发）。症状：飞书里 `/调用 print_design` 秒回"没有找到能力"，但服务器日志该时刻毫无动静、数据库里能力好好在。诊断法：对时——飞书消息时间 vs `docker logs` 有无活动。解法：同事关本机实例，本地调试要用独立测试飞书应用（2026-08-13 实锤）

- 飞书机器人下载消息图片需单独权限 `im:message:readonly`（错误码 99991672），开通后必须**创建新版本并发布**才生效。诊断法：docker logs 里搜 download_media（2026-08-13 实锤，开通当晚参考图链路即通）

- **半步接工艺坑（2026-08-14 实锤）**：商家的循环单元是"半步接"（相邻横向单元纵向错开半格32cm），不是四方平接。两个连环雷：① 按平接做的无缝图在半步接排列下竖缝对不上；② AI 生成的"无缝"肌理底同样是平接拓扑，垫底后照样现竖缝——底纹必须按晶格（v1=(W,H/2)）程序化生成。解法都在 zexin_bigtile.py `--half-drop`，出货前看 grid3x3 排列预览验缝。**接单先问清循环方式**，别默认平接。
- 复杂图矢量化超时（2026-08-14 17:47 大马士革花实案）：繁密多色图案 2 核描摹远超 265 秒，撞平台 300 秒红线。旧代码超时直接杀进程还谎称"转人工"。已改"后台续跑+取件"模式：超时不杀活，用户几分钟后重发"转矢量"直接取成品（带锁防重复开工、产物mtime验新）。豹纹级简单图不受影响仍一次出。

- TIFF 发飞书丢件（2026-08-14）：平台按 mime 前缀路由，image/tiff 走了飞书图片通道——**飞书图片接口不认 TIFF**，静默丢失还标"已投递"。解法：TIFF 按 application/octet-stream 申报走文件通道。给同事的顺手修：平台 send_artifact 路由应按飞书实际支持格式（jpeg/png/webp/gif）判断，不能只看 image/ 前缀。

- **平台容器日志时间是 UTC，宿主机是 CST（2026-08-15 实锤）**：`docker logs omni-agent-hub` 里的时间要 +8 才是北京时间（日志 23:30 = 北京 7:30）。对时排查（消息劫走诊断法、晨报准点验证）前先确认这层，否则会把准点误判成时区 bug。宿主机 journalctl/cron 是 CST 不用换算。

- **群聊必须@机器人，不@根本收不到（2026-08-17 捷通群实锤）**：应用缺 `im:message.group_msg`（接收群聊所有消息）权限，群里非@消息飞书压根不推送——症状是新群"机器人全无反应、控制台空白"，服务器日志零记录。诊断法：同群发一条@的一条不@的，对 `docker logs` 有无"已入队"。连环坑：**图片单独发同样丢**（纯图片消息带不了@），图文必须同一条消息。根治：开放平台该应用开通 im:message.group_msg + 创建新版本发布+管理员审批（同事地盘）。附：外部群（跨组织）实测机器人能进能回话，应用已开"允许加入外部群"；开权限后外部群能否收全量消息待实测。操作手册旧话术"@它或直接说"是错的，已修正。
- **"换一批"丢约束、主题却漂移回来（2026-08-17 实锤）**：调度器只看当前一句话，"再来一批"被改写成泛化需求——上一批点名的"大花位"约束丢了，主题倒经禁重名单渗漏回来（第二批混进中等/小花位的豹纹）。已修：`_CONTINUE_RE` 匹配纯换批话术（再来一批/换一批等）时继承 state 里的 `last_preference`，带新主题的"换一批国风的"正常覆盖；意图回显会显示"沿用上批偏好：…"。
- **豹纹画成花簇（2026-08-17 老板群实测逼出）**：方向生成的"差异化（抽象程度）"指令诱导模型写出"豹斑软化成云朵/格块"，生图照做后豹斑环结构全丢，看着像碎花。已修：`ANIMAL_RULE` 动物纹锚点死规则焊进 DIRECTIONS_SYSTEM+RENDER_SYSTEM（豹纹必含 leopard rosettes with broken dark ring outlines），差异化只许动配色/密度/花位；propose 用户提示里"抽象程度"一词已删。另注：**四宫格是缩略草图，保真度天生低，验收像不像要看"要N"的单张效果图**。
- 本机跑 test_agent.py 静默 exit 49 无任何输出：Git Bash 里 `python` 指向 WindowsApps 商店假货 stub，用 `py -3` 才是真解释器（2026-08-17）。
- **换色四连坑（2026-08-17 老板群实弹逼出，已修 fb0890e）**：①"5个配色只给3个"——调度规则写死最多3条，且提示词里的示例色调（青灰蓝调/赭金暖棕调/玫瑰粉米白调）被模型**每次照抄**（三次实测输出一字不差）：示例锚定，修法=recolor上限放宽到5+"禁止照抄示例词"；②"还有其他配色吗"没带图没说"这张图"，掉进 render 重新设计新图案——新增"追加配色"调度规则判 recolor；③识别回显"选7号"但 recolor 分支根本没把 selection 传给 do_recolor，一直换的是 last_renders 最后一张（纯巧合没炸）；④换色产物覆盖 last_renders，追加换色会在**色版上二次换色**越换越歪——state 新增 recolor_src（原图指针）+recolor_used（已用色调避重），新设计批次自动清换色会话。教训：**提示词里的示例即锚，低温下必被照抄，示例必须配"禁止照抄"**。
- **换错图·编号世界错位（2026-08-17 第7张实案，已修 d1ef30c）**：用户说"第7张换配色"指的是**宫格里的方向编号**，但宫格是一张拼图、方向没有单张成图；服务器 selection 索引的是 last_renders 留底，7 越界后旧兜底默默拿最后一张顶上——换出完全不相干的图。修法：编号对不上留底**必须明说并指路**（"宫格里的N是方向编号，先发要N出效果图"），绝不静默兜底。教训：**用户的编号世界（宫格方向号）≠服务器索引（留底序号），对不上时宁可拒绝+指路，不可猜**。
- **转矢量只吃第一个编号（2026-08-17"转矢量1 2 3只出1号"实案，已修 2ee8c04）**：`selection[0]` 只取头一个，回显却打全部编号——又是"回显装懂"（同日第二例：回显与执行不一致）。已改多编号排队：2核机器**单线程串行逐张**加工（并行挤爆CPU），先全上锁防重复开工，取件时出齐的都投、锅里的报号；文件名带编号（矢量-1.pdf）防同名覆盖；一次限3张、单条消息限投2张成品（PDF动辄9MB，3张全塞会撑爆投递）。教训：**凡带 selection 的模式，检查"回显的编号"和"执行吃的编号"是否同一份——回显骗人比不回显更毒**。

## 2026-08-18 商家实测批（捷通群）

- **"要图2 3 4"只出1张（已修 2ee8c04 之后的提交）**：`do_render` 把选中的多个方向揉进**一条**提示词（`base_need` 用"；"拼接），再 `generate_image(n=min(2,...))`——用户要3个方向，服务器只出1~2张合成图。修法：多编号走独立分支，一个方向一条提示词一张图、3路并行（一次最多3张防撞300秒线），`_save_renders(dirs=[...])` 记下方向号，文件名带"方向N"。**跟 2ee8c04 转矢量那个坑同一个病根**：回显吃了全部编号、执行只吃第一份。
- **编号世界错位续集**：出完方向2/3/4的效果图后，用户仍按方向号叫"图2"，服务器按留底序号数会取错图。已建统一映射 `_pick_render(renders, dirs, n)`：先认方向号、再认留底序号、都对不上返回 None（**绝不猜**），换色/转矢量/改图/成衣四个入口共用。改图编号对不上也改成明说，不再默默改最后一张。
- **"生成N种配色"被判成重新设计**：调度器每次只拿当前一句话去判（零历史），"生成4种配色"这类靠上文才成立的话必然猜错；且 render 的变体硬切3条，导致"要4给3还换了图案"。修法：`_RECOLOR_ONLY_RE` + 会话有留底图 → 强制 recolor（状态守门，不指望模型）；`do_recolor(want=N)` 按用户点名数量出色版（上限5），不足明说。
- **低温也会抖**：同一句"来一批豹纹的"、同样上下文，temperature=0.1 下 5 次里有 1 次判成 render（直接出效果图、不给8方向）。**式样固定的话术别交给模型**——`_BATCH_RE` 前置改判 propose（带配色词的除外，"换一批配色"仍走换色）。
- **"来一批"抹掉老图**：`do_propose` 原是 `state[conversation_id] = {...}` 整条覆盖，中途插一句换批就把 last_renders/last_prompts/换色原图全清零，前面出好的图当场断线（转矢量、取件、追加配色都找不到）。改增量更新。**连环风险**：老图留着以后，用户在新宫格下说"2号换配色"会按老图序号取到上一批的图——所以提案时清 `last_render_dirs`、新增 `batch`/`renders_batch` 批次戳，带编号的操作碰上老批次图一律明说指路，不带编号的照常吃老图。
- **成衣效果图链路（新能力）**：**apimart `/images/generations` 的 `image` 参数实测真吃参考图**（image / image_url / images 三种传法都收，用 image），出来的成衣上就是那张花而不是照描述重画——推翻此前"疑似收 image 参数、未验产物"的判死。参考图靠把留底复制到 `bigtiles/_ref/` 再走已有的 nginx `/zexin-files` 口给模型取（14天清理cron覆盖，不堆盘）。提示词死规则：花型与参考图一致（同元素同配色同尺度）、整件完全摊开无折叠堆叠、套装出上衣+裤子并排、**单件款必须写 single one-piece garment only, no pants**（不写就自己凑一条裤子）。成衣产物**不写 last_renders**——它是成衣照片不是印花图，进了留底会被后面的转矢量/换色拿去开工。
- **带图发的请求被老留底顶掉（回显装懂第四例，已修 f9aec90）**：六个模式里只有 recolor 接了"当条消息带的图"，mockup/vectorize/bigtile 都只翻 last_renders。捷通群实案：乔枫图文同条发墨绿底金花要做家居服，出来的成衣是紫底白花（上一张留底），**回显还写着"已读参考图"**——视觉解析确实跑了，执行那步压根没接。修法放在 `handle_task` 派活层统一守门（一处覆盖三个模式）。同根隐患顺带堵掉：带图说"转矢量"以前会矢量化上一张留底，**交厂文件出错图比颜色不对严重得多**。
- **教训（本项目内第4次复发，未跨项目故不晋升知识库）**：**回显与执行必须核对是同一份数据**。四例全是"回显说对了、执行拿的是别的"——转矢量只吃第一个编号、换色 selection 没传进去、编号越界默默兜底、带图请求用老留底。改任何带 selection / 带 images 的模式，先问一句：回显里报的那个东西，执行真的用到了吗。
- **成衣图版型随机（已知边界，未修）**：提示词只焊了花型一致/完全摊开/款式大类，领型、门襟、口袋、袖口、裤型全归模型发挥，两次"做成家居服"版型不一样。用户点名的细节会翻进提示词。等商家给默认款再焊死。

- **"要N"出来不是宫格里那张（2026-08-18 商家实弹，产品语义级问题，已修 affe706）**：旧版"要N"=拿方向N的**文字描述**重新生成——宫格是示意草图，按文字重画必然不同款。但商家的语义是**商品目录**：挑中1号=要1号那张图本身（"指定了号码出来都不是同一张，这个问题很大"）。修法吃当天 img2img 红利：提案宫格落盘（grid_paths 随批次覆盖）→"要N"切出N号格子（`_crop_grid_cell` 四分之一切法）挂公开口当参考图 → REFINE_EN 忠实精绘放大（同元素同构图同配色同尺度+去编号角标）。实测格子和成图同款同密度。**教训：用户看图选号的场景，"所见即所得"是硬语义——出给他看的每张候选图都要落盘留底，选中后必须从那张图出发加工，不能从描述文字重来**。注意两处配套：宫格丢了退文字路线（老会话兼容）；留底提示词存方向描述不存 REFINE_EN（改图要拿它当底稿）。
- **转矢量两连雷（2026-08-18 商家实弹田园碎花，已修 a72323c）**：①该图2核描摹15分钟，刚好蹭过900秒锁过期线——过期后再喊"转矢量"会判孤儿锁**重复开工**，双份进程挤爆2核雪崩。修法：判过期前先 `pgrep -f 源文件名`，进程活着=还在加工继续等。②同图 PDF 34MB 超飞书文件通道约30MB上限，硬塞 base64 会投递失败（又一例"标记已投递实际丢件"）。修法：collect 按大小分流，>28MB 复制到 bigtiles/vec/（ASCII名）走 nginx 下载链接，小文件照常附件。话术同步改实在："繁密复杂图可能要一二十分钟"。

- **程序换色把多色图压成单色（2026-08-18 拱门图实弹，已修换色v2）**：旧算法是明度 duotone（灰度→bg-fg 双色带），双色图（豹纹）看不出问题，**多色图的颜色层次全灭**——紫/蓝/褐拱门换完每张只剩单色深浅，商家："配色全是一样的"。v2=HSV 色相整体旋转到目标色调（各原色等距跟转保相互差异）+饱和度限幅靠拢+明度不动（层次/布纹全留）+低饱和底区单独染浅 bg。仍纯程序秒级零费用。**教训：验图像算法要拿多色图当测试件，双色图什么毛病都测不出来**。

- **同日多批留底文件同名互相覆盖（2026-08-18 深夜实锤，真凶级）**：留底名"泽鑫-日期-效果-N.png"每批从1编号，同一天第二批直接覆盖第一批文件。后果链：recolor_src 存的是**路径**，路径没变内容被掉包——"追加换色回原图"从文件层被架空，商家往色版上叠着换、怎么换都是那个色系；且换色v2/v3 调试时拿"原图"一直是被覆盖的色版（S中位50全图有色），算法背了文件层的锅。修法：留底名加时分秒戳。**教训：凡是"存路径引用文件"的状态，文件名必须全局唯一（带时间戳），否则同名覆盖=状态无声腐坏；排查图像算法前先验输入文件是不是你以为的那张（看S分布一眼便知）**。
- **换色v2整体转调也不行（2026-08-18 拱门图二连败）**：色相整体旋转对邻近色（紫蓝差30度）无区分力，转完仍挤一个色系；低饱和色被S阈值吞进底。v3=分色映射：色相直方图找峰聚主色簇，每簇按占比对齐4色调色板（主配主）单独替换，白底(S<=30)默认不动。RECOLOR_SYSTEM 从 bg/fg 色对改 bg+4色 colors。实测白底雏菊：花→蓝茎→褐多色并存。**商家随即定：底色也要变**——调色板 bg 字段染底区（V 不动保纹理），完整语义=底/花各归各位一起换。
