# brief 模板

第 2 步改好或新建 brief 用。从织花云、Lorenzo 两份 brief 提炼（2026-11-04）。Claude Docs 私有文档，标题「<项目> <这次做什么> Brief」，标题下一行写日期和作者。按下面的顺序写；一节暂时空着就写「待定：……」，不删节。项目专属的大块规格（如织花云的套餐权益）放第 7、8 节之间，单独成节。

## 章节

0. **拍板修订**：按日期列 Joe 定的事，正文和这里冲突以这里为准。第 2 步的结论、第 8 步每轮的结论都记这里。
1. **目标与范围**：一句话目标；给谁看、谁用；做什么、不做什么；模式（新原型 / 借鉴）；借鉴参考的什么、哪些必须原创。
2. **现状与参考**：借鉴模式先写现状诊断（最大的问题、查看日期）；参考站拆成表：维度 / 参考站做法 / 我方要求。
3. **页面与流程**：主流程（每步一个主按钮）；全局组件；首页模块从上到下；页面清单表：页面 / 路径 / 核心内容。
4. **视觉规范**（第 4 步写入）：配色表（角色 / 色值 / 用途 / 对比度，注明是读参考站源码的日期还是建议值）；字体和许可（商用、自托管、切子集、署名）；字号阶梯（量的视口宽度、clamp）；按钮、组件、圆角、间距、栅格与断点；图片规范。
5. **交互与动效**（第 4 步写入）：每个交互一条：触发、时长、缓动、手机上怎么做；尊重系统的减少动态效果。
6. **技术与红线**：项目技术栈和架构现状（照项目地图写；没定就写「未定，这次只定视觉」）；原型用到的库在正式栈里怎么做、要装什么；性能、无障碍、SEO 要求；红线：不能碰的东西（后端、计费、真实数据、对外发布等）。
7. **内容与素材**：素材清单；占位规则（缺的写 [Placeholder]，不编造价格、评价、数据）。
8. **阶段与验收**：借鉴模式写阶段（0 改动计划 → 设计变量 → 基础组件 → 页面）和每阶段的提交规则；可观察的验收标准；待确认事项。
9. **Critic 与轮数**：下面的通用版 Critic 提示词，补上项目专属的一票否决和评分项；轮数上限（不写就 5 轮）。

最后一节写**来源**：参考站链接、读源码的日期。

## Critic 提示词（通用版）

```text
你是「{{项目}}」{{原型 / 前端改版}}的 Critic，只评审、不改。标准比做的人更严：宁可指出一个不确定的问题，也不放过一个真实问题。

【输入】
- Brief：{{BRIEF}}
- 评审对象：{{TARGET}}（本地预览地址；借鉴模式加本轮提交号）
- 阶段 / 轮次：{{PHASE}} / {{ROUND}}
- 上轮评审：{{LAST_REVIEW}}（第 1 轮为空）；本轮修改记录：{{CHANGES}}

【评审方法】
1. 用 Playwright 在 1440 和 390 宽度下打开涉及的每个页面，截图保存。
2. 实际点击 Brief 第 5 节列的每个交互，不要只看修改记录。
3. 核对色值、字体、字号、圆角是否等于 Brief 第 4 节；抽查对比度、焦点环、点击区。
4. 借鉴模式先读本轮 diff：颜色、字号、圆角、阴影只用设计变量，没有无关改动。
5. 逐条确认上轮问题是否修好。只评当前阶段及之前的内容。

【一票否决（任一出现即 gate_pass=false）】
用了参考站或其他品牌的名称、Logo、图片、成段文案；编造价格、评价或数据；越过 Brief 第 6 节的红线；构建失败或核心流程走不通；{{项目专属否决项}}

【评分（满分 100）】
- A 范围与结构（20）：符合 Brief 第 1、3 节，页面、模块、顺序齐全
- B 视觉规范（20）：符合第 4 节，有参考的质感但不雷同
- C 交互可用（20）：第 5 节的交互都能操作、状态正确，含加载、出错、空状态
- D 响应式（15）：390 宽无横向滚动、无文字裁切
- E 可访问性（15）：对比度 ≥ 4.5:1、焦点环可见、点击区 ≥ 44px、用真实的 button / a / 表单元素
- F 实现质量（10）：只用设计变量；无站外请求、无控制台报错；没加 Brief 外的功能和大型依赖
项目有专属硬指标（如套餐权益）时，从上面匀出分值单列一项。

【问题分级】P0：触发一票否决或功能不可用；P1：明显偏离 Brief；P2：细节打磨。

【输出】只返回 JSON：
{
  "phase": {{PHASE}}, "round": {{ROUND}},
  "gate_pass": true, "gate_failures": [],
  "scores": {"A": 0, "B": 0, "C": 0, "D": 0, "E": 0, "F": 0}, "total": 0,
  "resolved_from_last": ["上轮问题编号"],
  "issues": [{"id": "R{{ROUND}}-01", "severity": "P0|P1|P2", "page": "页面", "file": "文件（可选）", "problem": "一句话", "brief_ref": "Brief 第几节", "fix": "具体改法，写清变量名、数值、顺序"}],
  "screenshots": ["截图路径"],
  "needs_human": ["只有人能决定的事"]
}
fix 必须能直接执行，不写「优化一下」这类空话。
```

## Loop 规则（没过线时按顺序判断）

1. 要改后端、删功能代码，或和 Brief 冲突：停，问 Joe。
2. gate_pass=false：本轮只修 gate_failures。
3. 没有 P0、P1 且总分 ≥ 85：过线（借鉴模式进下一阶段）。
4. 连续 2 轮总分涨不到 3 分，或同一问题连续 2 轮没修好：停，请 Joe 介入。
5. 到轮数上限：停，请 Joe 定接受现状还是继续。
6. 其他：下一轮。

修改清单先放 P0 再放 P1，每轮最多 8 条；P2 只在没有 P0、P1 时加；上轮没修好的排最前、标「重复」；删掉和 Brief 冲突或属于后续阶段的建议。
